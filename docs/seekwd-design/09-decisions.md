# 架构决策记录

## D-001：Seekwd 不依赖预先知道的节点库

- 状态：已确认
- 决策：Agent 可以探索未知应用、工具、Agent 和环境；节点库是开放的。
- 原因：用户不应被要求提前知道某个具体应用、协议或工具名称。

## D-002：一切能力统一为节点

- 状态：已确认
- 决策：AI、Agent、代码、工具、人工操作、环境操作、跨画布调用和触发器都拥有节点表示。
- 原因：统一观察、调试、权限、重试和审计模型。

## D-003：节点支持粗粒度与细粒度双向转换

- 状态：已确认
- 决策：复杂节点可以展开、拆分；多个节点可以封装为复合节点；历史运行保持不变。
- 原因：普通用户需要一句话完成，专业用户需要像调试程序一样控制。

## D-004：外部 Agent 不是系统边界

- 状态：已确认
- 决策：外部能力提供者是可探索、可委派的能力来源，不强制内置或固定封装。
- 原因：系统要能处理未知能力和未来出现的新执行单元。

## D-005：运行时图修改使用 GraphPatch

- 状态：已确认（正式合同见 [27-normative-contracts/05-graph-patch-protocol.md](27-normative-contracts/05-graph-patch-protocol.md)）
- 决策：Agent 修改图必须产生结构化 `GraphPatch`，经校验、权限判断和必要审批后应用；运行中的未来计划调整必须使用独立 `RunPatch`。
- 原因：防止静默改变运行图，支持审计、回滚和版本化。

## D-006：执行位置和环境分离

- 状态：已确认
- 决策：执行位置与运行环境是两个独立对象；节点声明需求，调度器负责匹配。
- 原因：同一能力可以在多个位置和环境执行。

## D-007：目标优先于实现方式

- 状态：已确认
- 决策：系统先定义要完成的目标、交付物、成功标准和授权范围，再寻找、组合或构造实现能力。
- 原因：具体应用、工具、协议和领域只是个别实现，不能成为 Pong Agent 的产品边界。

## D-008：运行时支持逐步细化

- 状态：已确认
- 决策：目标可以先以高层节点执行，随后按需要展开为更细的节点、子图或多个画布；细化和重新封装都保留历史关联。
- 原因：既要让普通用户用自然语言完成任务，也要让专业用户逐步调试内部因果链。

## D-009：执行单元是开放集合

- 状态：提案
- 决策：执行单元可以来自已有能力、外部能力、人工协作、动态组合或新建实现，核心系统只依赖统一契约。
- 原因：系统必须能够处理设计时未知的能力，而不是把未知情况归为异常。

## D-010：人类和 Agent 是平等操作主体

- 状态：已确认
- 决策：人类和 Agent 都可以创建、修改、审查和执行节点图；构建主体与执行主体分别配置，可以在运行中切换。
- 原因：用户可能只搭建框架、只委派局部、完全手工执行、完全自动执行，或在同一任务中反复接管和交还控制权。

## D-011：画布和节点是运行时语言的一部分

- 状态：已确认
- 决策：画布定义为可调用、可版本化的图模块；节点定义为有端口、执行、验证、失败和权限契约的最小可调度责任单元。
- 原因：节点图必须成为 Pong Harness 的正式运行时语言，而不是仅用于可视化展示的前端数据结构。

## D-012：基础语义必须独立于具体实现

- 状态：已确认
- 决策：身份、版本、Schema、事件、状态机、错误、执行上下文、主体、策略、表达式、存储和扩展协议作为独立基础层定义。
- 原因：前端、Agent、调度器和外部适配器必须共享同一套可验证语义，不能各自解释节点和画布。

## D-013：核心服务按事实所有权分界

- 状态：已确认
- 决策：目标、图、运行、执行、产物、观察、验证、策略、记忆和审计按各自事实来源分离，通过命令、事件和版本化引用协作。
- 原因：避免 Agent、UI、调度器和执行器直接改写彼此状态，保证恢复、审计和未来拆分部署的可靠性。

## D-014：标准节点库是 Harness 的最小图语言

- 状态：已确认
- 决策：控制、数据、等待、迭代、人类协作、Agent 协作、能力、画布、验证、错误、缓存、检查点与调试原语以版本化标准节点形式提供；具体领域能力通过扩展接入。
- 原因：人类、Agent、编辑器和调度器必须共享同一套跨领域原语，避免把业务或供应方细节固化进核心运行时。

## D-015：本地 Host 是可信控制平面

- 状态：已确认
- 决策：Seekwd Workbench 作为用户界面，Pong Host 作为用户设备上的控制平面和事实协调边界，节点执行通过受控执行上下文进行。
- 原因：长期运行、权限、持久化、扩展和恢复不能依赖一个前端页面或某个具体执行器进程。

## D-016：参考实现采用桌面本地优先的 Rust / TypeScript 架构

- 状态：提案
- 决策：默认实现使用 Tauri 2 承载 Workbench，React + TypeScript 提供编辑器，Rust + Tokio 提供 Pong Host 与 Harness，SQLite + WAL 保存事实与投影，大内容采用内容寻址 Artifact Store；图语义通过独立 Schema 与渲染器适配层表达。
- 原因：该组合能在用户设备上提供常驻运行、进程与权限控制、离线持久化和复杂 IDE 式画布，同时不把领域模型绑定到任何一个 UI 或节点执行语言。

## D-017：先实现可验证的核心，再接入 UI、Agent 与扩展

- 状态：已确认
- 决策：实施按领域值对象与 Schema、图校验、运行状态机、持久化与执行契约、Host IPC、Workbench、Agent/扩展的依赖方向推进。每层都必须有可执行测试和明确边界后，下一层才可依赖它。
- 原因：画布 UI 或模型调用无法替代运行事实、版本、取消、恢复和权限的正确性；倒置实施顺序会把核心缺陷隐藏在演示界面中。

## D-018：跨组件合同集中到 Normative Contract Layer

- 状态：已确认
- 决策：`27-normative-contracts` 是身份、版本、入口、状态、GraphPatch、跨画布投递、副作用、权限和保留策略的唯一正式合同源。其他目录可以保留概念、历史和实现说明，但冲突时必须引用并服从该目录。
- 原因：提案、未实现和正式协议必须可区分，避免前端、Host、Agent 和扩展 SDK 读取不同语义。

## D-019：Draft、Revision、Release 分层

- 状态：已确认
- 决策：CanvasDraft 是可变编辑对象；CanvasRevision 是不可变保存快照；CanvasRelease 是可调用的稳定发布对象。正式运行引用 Release，调试运行引用明确标记的 Revision；Draft 不得直接运行。
- 原因：运行事实必须绑定不可变图，发布和编辑不能互相改写。

## D-020：默认入口与命名入口并存

- 状态：已确认
- 决策：每个 CanvasRevision 必须且只能有一个 `defaultEntrypointId`，同时允许多个命名入口和触发器。`primaryNodeId` 仅作为迁移字段，不能代表全部入口。
- 原因：手动运行需要稳定默认入口，而事件、定时、Webhook 和父画布调用需要独立入口。

## D-021：统一状态注册表

- 状态：已确认
- 决策：Goal、Run、NodeRun、ExecutionHandle、ApprovalRequest、ApprovalGrant 和 ExecutionContext 的状态集合、终态、恢复、重试、人工处理和下游传播规则统一定义在 `27-normative-contracts/04-unified-state-registry.md`。
- 原因：相同词汇在不同服务中不能产生不同调度和 UI 语义。

## D-022：GraphPatch 与 RunPatch 分离

- 状态：已确认
- 决策：GraphPatch 只修改未来的 Draft/Revision 结构并产生审计版本；RunPatch 只调整尚未执行的运行计划，不得改写已发生事实或绕过图策略。两者必须使用不同命令、权限和审计类型。
- 原因：Agent 修复不能通过修改历史图或运行记录制造成功。

## D-023：跨画布采用至少一次投递和幂等去重

- 状态：已确认
- 决策：跨画布调用以 `invocationId`、`deliveryId` 和幂等键标识，至少一次投递；消费者按事件和调用去重，父子 Run 通过关联 ID 恢复。Call and Wait 与 Fire and Continue 的传播和失败策略由正式合同定义。
- 原因：断线、重试和进程重启不可避免，恰好一次投递不能作为基础假设。

## D-024：权限不是布尔值

- 状态：已确认
- 决策：代理权限必须由资源范围、能力、网络、秘密、预算、时限、后台执行和审批绕过边界组成的 AuthorityProfile 表达；任何扩大都触发重新评估或审批。
- 原因：`fullAccess: true` 无法表达也无法审计真实风险。

## D-025：LocalRestricted 是首个受限执行配置

- 状态：已确认
- 决策：开放执行前必须提供 LocalRestricted：只读工作区、默认禁网、禁止秘密和依赖安装、资源/进程/输出/时长限制、可取消，并明确结果未知处理。Docker、远程和不受限本地执行属于后续独立配置。
- 原因：图语义成熟不等于任意代码和副作用执行安全。
